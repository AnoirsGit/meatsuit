# Задание: доработки meatsuit по итогам живого Тиндера

Контекст: бот `../tinder-matcher` работает поверх meatsuit. 2026-10-07 его впервые проверили на живом Тиндере (чтение списка, вкладки, ввод без отправки). Бот обошёл несколько ограничений meatsuit у себя; их место здесь. Читать до начала: `docs/04-contract.md` (контракт), `index.js` (`connect`, `task`), `window.js` (`openWindow`), `hands.js` (`act`, `see`, ветка dryRun), `limits.js`, `supervise.js`.

Правила работы: самое маленькое правильное изменение; каждое изменение поведения — с тестом и правкой `docs/04-contract.md`; существующие тесты не ослаблять и не удалять (если мешает, остановиться и спросить); не коммитить без просьбы. В рабочем дереве уже лежат незакоммиченные правки (`README.md`, `docs/04-contract.md`, `hands.js`, `index.js`, `package.json`) и новая папка `docker/` — это чужая работа, не сбрасывать и не смешивать с задачей.

Приоритеты: **1 → 2 → 3** нужны боту сейчас, 4 желательно, 5–6 как бэклог.

## 1. Режим «одна вкладка» для площадки

**Проблема.** `task()` в `index.js` на каждую задачу вызывает `openWindow(browser)` (новое окно) и закрывает его в `finally`. Тиндер держит одну активную вкладку: в предыдущей он показывает «You Opened Tinder In a New Tab» + кнопку «Make this my active tab» (наблюдалось на живом, скриншот). Человек в зеркале (Neko) теряет сессию вкладки при каждой задаче бота.

**Что сделать.** Необязательное поле площадки в `sites.json`, например `"singleTab": true`. Для такой площадки `task()` не открывает окно, а работает в уже существующей вкладке этой площадки (найти по хосту); если вкладки нет, открыть одну и оставить её после задачи (не закрывать).

**Важно знать.** При проверке с Debian Chromium `browser.contexts()[0].pages()` после `connectOverCDP` вернул пустой список, хотя вкладка Тиндера была открыта (`/json/list` её показывал). С Google Chrome 154 это не перепроверялось. Исполнитель должен сначала выяснить, видит ли Playwright существующие страницы; если нет, искать вкладку через `Target.getTargets` и подключаться к ней (CDP-сессия на уровне страницы).

**Готово, когда:** тест на фальшивой площадке: две подряд задачи с `singleTab` работают в одной вкладке, число вкладок до и после одинаково, вкладка человека не закрыта; без флага поведение прежнее (окно на задачу). `docs/04-contract.md` описывает флаг.

## 2. Ожидание готовности страницы (SPA)

**Проблема.** `see()` сразу после `goto` отдаёт пустой снимок на SPA (`text: ''`, `elements: []`, наблюдалось на tinder.com/app/recs): `waitForLoadState('domcontentloaded')` в `hands.js` не ждёт отрисовку. Каждый проект сейчас пишет свой цикл ожидания (в боте это `openApp` в `agent/page.js`).

**Что сделать.** Опция у `see()`, например `see({ settle: { minElements: 3, quietMs: 500, timeoutMs: 10000 } })`: ждать, пока DOM перестанет меняться и интерактивных элементов будет не меньше порога; по таймауту вернуть последний снимок (не бросать). Вариант попроще, если укладывается: поле `ready` в `wait` (`{cmd:'wait', until:'elements', min:N}`). Выбрать одно, обосновать в контракте.

**Готово, когда:** тест со страницей, которая рисует элементы через 2 секунды: `see({settle})` возвращает непустой снимок, обычный `see()` как раньше. Таймаут не бросает исключений.

## 3. dryRun: безопасная навигация кликом

**Проблема.** В dryRun выполняется только `goto` (`hands.js`, ветка `if (dryRun && c.cmd !== 'goto')`). У Тиндера список чатов — вкладки Matches/Messages (`role=tab`) в боковой панели, переключаются кликом, поэтому в dryRun виден только первый список. Контракт «в dryRun только goto» закреплён тестами бота (e2e), поэтому ослаблять его целиком нельзя.

**Что сделать.** Явное, узкое исключение: в dryRun выполняется `click` по элементу с ролью `tab` (чтение-навигация внутри страницы). Остальные клики, ввод и клавиши по-прежнему только в журнал. Рассмотреть, нужно ли это ограничить опцией `task({ dryRunNavigation: true })`, чтобы поведение по умолчанию не менялось.

**Готово, когда:** тест: в dryRun клик по `role=tab` меняет страницу, клик по `button`/`link`/`textbox` и `fill`/`press` не выполняются и пишутся как `dry-run`; контракт обновлён; тесты проекта `../tinder-matcher` (`npm test`, e2e) остаются зелёными или явно обновлены вместе с контрактом.

## 4. Слоты лимита: чтение не должно стоить как запись

**Проблема.** `task()` вызывает `reserve(site, rule, ...)` на каждую задачу. В Тиндере `perDay: 20`, а боту нужны задача на список и задача на каждый чат (в том числе на проверку «ответила ли она», где ничего не отправляется). 20 слотов кончаются на ≈19 чатах; проверки молчащих лидов съедают слоты, нужные для приветствий.

**Что сделать.** Вариант: задача, объявленная `readOnly: true`, тратит только `perHour`, а `perDay` не тратит; если внутри она выполнила команду записи (`fill`, `type`, `click` по не-tab, `press` Enter), `supervise` засчитывает полный слот задним числом. Лимит `perHour` оставить как защиту от частоты. Не ослаблять защиту площадки по умолчанию: без флага всё как сейчас.

**Готово, когда:** тесты `limits`/`task`: read-only задача не уменьшает дневной остаток; та же задача с записью — уменьшает; без флага поведение прежнее.

## 5. Бэклог: известные слабости (из `docs/05-handoff.md`)

- `guard` и `eyes` не видят shadow DOM.
- Замок очереди (`lock`) уязвим при гонке нескольких ждущих процессов.
- Playwright включает `Runtime.enable`; Patchright не подключён, эффект на реальных площадках не проверен.
- `exit_type`/профиль: при `docker stop` без `stop_grace_period` Chromium может не сбросить профиль (см. `docker/docker-compose.chrome.yml`, `stop_grace_period: 30s`).

## Как проверить результат

`node --test` в `meatsuit`; затем `npm test` в `../tinder-matcher` (132 теста, из них e2e на настоящем Chromium). Отчёт в конце: что изменено, почему безопасно, что будет, если ошибка.
